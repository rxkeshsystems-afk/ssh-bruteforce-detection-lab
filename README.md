# Lab 01 — SSH Brute-Force & Password-Spray Detection

**Author:** Rakesh Rajbali · **Focus:** Blue team / log analysis · **MITRE ATT&CK:** T1110.001, T1110.003, T1078

## Objective
Build a Python detector for Linux `auth.log` that finds SSH brute-force activity, then use it to investigate a day of logs from a simulated production server (`web-prod-01`). The main goal is to catch the attack that simple rate-based rules miss.

## Environment
| Item | Value |
|---|---|
| Language | Python 3 (standard library only) |
| Data | Synthetic `auth.log`, 664 lines, 24 hours (`logs/auth.log`) |
| IP space | RFC 5737 documentation ranges, so no real hosts are involved |

The log is generated by `src/generate_logs.py` with a fixed seed, so anyone can reproduce it. It has normal admin logins (including an occasional typo) plus three hidden attack patterns.

## How to Run
```bash
cd src
python3 generate_logs.py                                   # build logs/auth.log
python3 detect_bruteforce.py ../logs/auth.log --year 2026 --json ../output/alerts.json
```

## Detection Logic
| Rule | Fires when | ATT&CK |
|---|---|---|
| `BURST` | ≥ 20 failures from one IP inside a 2-minute sliding window | T1110.001 |
| `SPRAY` | One IP fails against ≥ 5 distinct usernames | T1110.003 |
| `SLOW` | ≥ 15 total failures from one IP that never trip `BURST` | T1110.001 |
| `COMPROMISE` | A **successful** login from an IP with ≥ 5 earlier failures | T1110 → T1078 |

`Invalid user` lines are skipped because each one is paired with a `Failed password` line for the same attempt, so counting both would double the numbers.

## Results
```
== SSH Brute-Force Report: ../logs/auth.log
   failed attempts: 494 | source IPs with failures: 6 | successful logins: 61

[CRITICAL] COMPROMISE 203.0.113.200   T1110 -> T1078  Accepted password for 'deploy' at 2026-11-14 14:55:25 after 38 prior failures
[HIGH    ] BURST      203.0.113.45    T1110.001       138 failures in 2 min (peak starting 2026-11-14 03:14:37)
[HIGH    ] BURST      192.0.2.77      T1110.001       33 failures in 2 min (peak starting 2026-11-14 09:40:03)
[HIGH    ] SPRAY      192.0.2.77      T1110.003       failed against 16 distinct usernames
[MEDIUM  ] SLOW       203.0.113.200   T1110.001       38 failures spread over 13:08:38 (evades rate-based rules)
```
The full output is in `output/report.txt` and `output/alerts.json`.

**False positives: 0.** The three legitimate admins (`198.51.100.0/24`) had occasional typos, but none crossed a threshold.

## Findings
1. **Compromise (CRITICAL): `203.0.113.200` → `deploy`.** The attacker tried about one password every 18–26 minutes for 13 hours, then logged in successfully at 14:55:25. At that pace, a typical fail2ban setting (`maxretry=5` within `findtime=10m`) **would never have banned it**. Only correlating failures with a later success exposed it. The account should be treated as compromised.
2. **Fast brute force (HIGH): `203.0.113.45` → `root`.** 400 attempts in about 6 minutes, peaking at 138 in 2 minutes. No successful login. This is noisy, automated scanning.
3. **Password spray (HIGH): `192.0.2.77`.** Common service and default account names (`admin`, `oracle`, `postgres`, `pi`, `ec2-user`, …). 16 usernames, none of which exist on the host.

## Incident Response (for Finding 1)
- **Contain:** lock `deploy` (`usermod -L deploy`), kill its sessions (`pkill -u deploy`), and block `203.0.113.200` at the firewall.
- **Scope:** review `deploy`'s shell history, `~/.ssh/authorized_keys` (look for added keys), cron jobs, and outbound connections made after 14:55.
- **Eradicate/recover:** rotate the credential, remove persistence, and redeploy from a known-good image if tampering is found.

## Hardening Recommendations
- Set `PasswordAuthentication no` and require keys for every account, especially service accounts like `deploy`.
- Set `PermitRootLogin no`.
- Add MFA (e.g. `pam_google_authenticator`) wherever passwords have to stay.
- Pair rate-based banning with **long-window** rules (failures per IP per 24h) and **fail-then-success** correlation in the SIEM.
- Restrict SSH to a VPN or an allowlist of admin IPs.

## What I Learned
Threshold-based detection only catches noisy attackers. The dangerous attacker in this log was the quiet one, and the signal that exposed it was the *sequence* of failures followed by a success, not the volume. Writing the detector also made clear how log quirks (like paired `Invalid user` lines) can quietly skew counts if you don't account for them.
